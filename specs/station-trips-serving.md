# Spec: Serve Per-Station `ymdgtb_cd.json` from the DVX Cache

## Goal

Serve the 2,606 per-station `ymdgtb_cd.json` files (generated by
`ctbk station-trips-json`, DVC-tracked as
`s3/ctbk/stations/ymdgtb`) directly from the public S3 DVX cache,
without duplicating them into `www/public/` or adding a D1 / Worker
layer.

Supersedes the "Option A: copy into `www/public/`" approach from
`specs/station-trips-static-json.md`. 211 MB of uncompressed JSON in the
Vite bundle is a non-starter, and a Worker / D1 is unnecessary for
read-only static data that already lives in our content-addressed cache.

## Background: what we already have

- `s3/ctbk/stations/ymdgtb.dvc` tracks the whole directory as one
  artifact, md5 `4e913e21…`
- DVX remote: `s3://ctbk/.dvc/` (see `.dvc/config`)
- Every file lives at
  `s3://ctbk/.dvc/files/md5/<md5[0:2]>/<md5[2:]>`
- The `ctbk` bucket already has a **public** `s3:GetObject` policy,
  so URLs like
  `https://ctbk.s3.amazonaws.com/.dvc/files/md5/33/2fc44b2e3c21dee0acb628c5eaf111`
  are already reachable without any CloudFront or Worker in front
- Per-station egress is tiny (~100 KB average, ~17 KB if the client
  accepts gzip from the S3 edge — but S3 does not gzip on the fly, so
  expect raw ~85 KB average)
- Content-addressing means every URL is permanently cacheable
  (`Cache-Control: public, max-age=31536000, immutable`)

## Plan

### 1. Manifest generation

When the `ymdgtb` directory is rebuilt, emit an accompanying
`ymdgtb-index.json`:

```json
{
  "dir_md5": "4e913e21e182872470161ce6e9efa05f",
  "files": {
    "5297.02": "332fc44b2e3c21dee0acb628c5eaf111",
    "5578.02": "8e07a0c2ed4c04f00f928540d9a0a469",
    ...
  }
}
```

Size: 2,606 entries × ~55 bytes ≈ ~140 KB raw, ~40 KB gzipped. Ship it
as a static asset in the site build.

Easiest source: the `.dir` file DVX already writes to
`s3://ctbk/.dvc/files/md5/4e/913e21e182872470161ce6e9efa05f.dir`. That
file is a JSON array of `{md5, relpath}`. The manifest is essentially a
pivot into `{relpath_without_ext: md5}`.

Where to generate:
- Extend `ctbk station-trips-json` to write `ymdgtb-index.json` next
  to the directory (e.g. `s3/ctbk/stations/ymdgtb-index.json`,
  committed to git directly since it's small enough)
- **Or**: let the build step derive it on the fly from the DVX `.dir`
  file. Cleaner because the index is always in sync with whichever
  `ymdgtb.dvc` commit the site is building from.

Recommendation: **derive at build time** from the `.dvc` md5 plus the
S3-hosted `.dir` file. One fetch during build, one write to
`www/public/ymdgtb-index.json`. Keeps `ctbk station-trips-json` focused
on data generation.

### 2. Client fetch

```ts
// Module loaded once per StationDetail mount (or at App root, then cached)
const index = await fetch('/ymdgtb-index.json').then(r => r.json())

function trips_url(short_name: string): string {
  const md5 = index.files[short_name]
  if (!md5) throw new Error(`no ymdgtb data for ${short_name}`)
  return `https://ctbk.s3.amazonaws.com/.dvc/files/md5/${md5.slice(0,2)}/${md5.slice(2)}`
}

const rows = await fetch(trips_url(short_name)).then(r => r.json())
```

Cache strategy:
- `ymdgtb-index.json`: short TTL (e.g. 1 hour), since it changes when
  monthly data rebuilds. Could also be cache-busted by bundling a
  content hash into the URL (`/ymdgtb-index-<hash>.json`) if we want
  aggressive long-term caching.
- Per-station files: immutable forever (content-addressed URL).

### 3. Migration / drop the old approach

- Delete the `load_station_trips_monthly.py` D1 loader (or leave
  deprecated — it was never wired into the live `StationTripsChart`
  that shipped in `e4718054`).
- `StationDetail` switches from whatever it's fetching today to the
  manifest + direct S3 fetch.
- Aggregated parquets (`ymrgtbs_cd_<ym>.parquet`,
  `ymrgtbe_cd_<ym>.parquet`) remain as the upstream source.

## Open questions

- **Manifest location in site**: `/ymdgtb-index.json` at the root, or
  under `/assets/`? Pick to match existing convention.
- **Manifest format**: flat `{short_name: md5}` is simpler; the
  `{dir_md5, files: {...}}` wrapper lets us show "data version" in
  the UI if we ever want to.
- **CORS**: `https://ctbk.s3.amazonaws.com` — does the bucket have
  a CORS policy allowing `GET` from `ctbk.dev`? Needs verification
  before flipping the frontend over. If not, add one (or use a custom
  domain via CloudFront / CF).
- **CF in front of S3 later?** Could add `data.ctbk.dev` with CF
  proxy for gzip-on-the-wire + free egress. Worth revisiting if
  egress or performance becomes noticeable. For now, direct S3 is
  fine.
- **Rebuilds and cache freshness**: when a new month lands and
  `ymdgtb` is regenerated, most station files are unchanged → same
  md5, same URL, cache still valid. Only changed stations get new
  URLs. Nice property.

## Phases

1. Verify CORS on `ctbk` S3 bucket (add `GET` allow for `ctbk.dev`
   origins if missing)
2. Add a build step (Vite plugin / prebuild script) that reads
   `s3/ctbk/stations/ymdgtb.dvc`, fetches the `.dir` manifest from
   S3, and writes `www/public/ymdgtb-index.json`
3. Switch `StationDetail` to manifest + direct S3 fetch
4. Remove or deprecate the D1 loader / trips API endpoint
