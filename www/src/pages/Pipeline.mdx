# Data Pipeline

<PipelineProvider>

The ctbk data pipeline transforms raw Citi Bike trip data through several processing stages, from raw ZIP archives into analysis-ready aggregations. This page documents each stage and lets you explore the <PipelineStats /> that make up the complete pipeline.

<PipelineDiagram />

<H2 id="source-data">Source Data</H2>

[Citi Bike][citibike] publishes monthly trip data as ZIP files on a public S3 bucket at [`s3://tripdata`][tripdata-index]. Each ZIP contains a CSV with one row per ride, including start/end times, stations, and (historically) user demographics.

<StageByKey stageKey="zip" />

[citibike]: https://citibikenyc.com
[tripdata-index]: https://tripdata.s3.amazonaws.com/index.html

<H2 id="normalization">Normalization</H2>

The raw ZIPs contain CSVs with inconsistent schemas across years—column names change, new fields are added, and NYC/Jersey City data is published separately. The normalization stage reads the CSVs directly from the ZIPs, harmonizes these differences, merges regions, and produces consistent Parquet files.

Each normalized month directory contains Parquet files split by start and end months. For example, `normalized/202006/202005_202006.parquet` contains rides from the June 2020 tripdata zips that started in May 2020 and ended in June 2020.

<StageByKey stageKey="norm" />

<H2 id="consolidation">Consolidation</H2>

After [normalization], the "consolidation" stage combines all records that *end* in a given month into a single canonical Parquet file. This is the primary representation used for downstream analysis — and the tile source for the **rides rollup-pyramid** that now serves every rides chart on the site (see [Serving](#serving) below).

<StageByKey stageKey="cons" />

<H3 id="legacy-data">Aside: Legacy Data Preservation</H3>

Several data-quality changes occurred around February 2021 (presumably as part of [the Lyft acquisition][lyft-acquisition]):

- **Gender/demographics removed**: Lyft stopped publishing **Gender**, **Birth Year**, and **Bike ID**. Those fields were also later retroactively scrubbed, back to January 2020. This is unfortunate: the original data showed a [notable increase in the proportion of women riders][gender-example] during 2020, a trend [observed in other cities][women-biking].
- **E-bike data timing**: JC/HOB e-bike data only begins February 2021 (vs. January 2020 for NYC). See [this example][ebike-example].
- **User type naming**: The values changed from "Subscriber"/"Customer" to "member"/"casual".
  - The former refers to annual pass holders, the latter to others (single ride, day pass, or 3-day pass).
  - This site displays them as "Member"/"Customer".

[lyft-acquisition]: https://www.lyft.com/blog/posts/lyft-becomes-americas-largest-bikeshare-service
[ebike-example]: https://ctbk.dev/?s=b&b=ce&r=jh&y=m&d=2001-

[ctbk.dev] has retained copies of the original 2020-2021 files (before Lyft's retroactive scrubbing) in `normalized/v0/`:

<StageByKey stageKey="v0" />

The original `v0` files are single parquets per month, essentially "consolidated" Parquets from an earlier version of these pipelines. I didn't save the original "tripdata" zip files, so these Parquets are my starting point for reconstructing the original data, and merging it in to the latest version.

To integrate with the main pipeline (which expects normalized files split by source/start/end month), they're "partitioned" into the same structure:

<StageByKey stageKey="partition" />

During [consolidation], for months January 2020 through January 2021, the partitioned `v0` records are joined with the newer (scrubbed) data, to backfill the missing columns. Since there's no canonical join key, the merge uses heuristics—matching on start/end times—which works reliably for most records.

[women-biking]: https://www.peopleforbikes.org/news/more-women-are-biking-than-ever-before

<H2 id="aggregation">Aggregation</H2>

The "aggregation" stage computes histograms over each month's rides, grouping by various dimensions and summing different metrics:

**Grouping keys:**
- `y` (year), `m` (month), `d` (day), `h` (hour)
- `r` (region: NYC or JC)
- `g` (gender), `t` (user type: subscriber or customer)
- `b` (bike type: classic, electric, or docked)
- `s` (start station), `e` (end station)

**Sum keys:**
- `c` (ride count)
- `d` (total duration in seconds)

For example, `aggregated/se_c_202306.parquet` groups by start and end station, summing ride counts. These aggregates are build inputs (station-pair JSONs, the per-station `ymdgtb` JSONs, and the legacy `ymrgtb_cd.json`); the live rides charts are served from the pyramid, not these files directly.

<H2 id="per-station-pages">Per-Station Pages</H2>

Each `/s/:slug` detail page pulls two orthogonal data streams:

- **Monthly trip history**, by default from the **rides pyramid** (`/api/rides-v3`, per-station identity keys). The `ymdgtb-cd` stage — per-station variants of `ymrgtb-cd` with start/end-station facets, one JSON per *canonical* station indexed at build time into `ymdgtb-index.json` — remains as the `?tsrc=legacy` fallback. Stations renumbered over time (e.g. `HB106` today, `HB609` pre-2025-06) share a file keyed by their canonical short_name; the index is enriched with alias entries so client lookups by either form resolve to the same data.
- **Live availability** (per-minute bikes/docks/disabled snapshots) from a separate GBFS pipeline: a Cloudflare Worker polls `station_status` each minute; recent data is served from a D1 hot cache and older data from R2 parquet archives (compacted by `compact-r2.py`). This serving path is mid-migration to R2-only (`specs/gbfs-r2-only.md`).

<H2 id="serving">Serving</H2>

The homepage rides chart and every `/s/:slug` trips chart are served by the **pyrmts** rollup-pyramid — `normalized/*.parquet` tiles rolled up (minute → … → month) on AWS Batch, registered in a Cloudflare D1 shard registry, and served by the CF api worker (`/api/rides-v5` in prod, `/api/rides-v3` rollback). This superseded the single-plot `ymrgtb_cd.json` flow. See `specs/rides-v5.md` and `specs/multiscale-timeseries-backend.md`.
